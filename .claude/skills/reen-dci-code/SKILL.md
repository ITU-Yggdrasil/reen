# DCI Code Realisation in Rust (Reen)

When implementing or reviewing Rust code generated by Reen, follow these conventions.

## Struct Layout

- **Context**: fields = role players + props. Role player fields are typed by the data/projection name from the manifest.
- **Data**: fields = attributes. Public struct with named fields.
- **Projection**: single `source` field referencing the underlying data type.

## Method Naming

- **Functionalities** → `pub fn <snake_case_name>(&mut self)` on the context struct.
- **Role methods** → `fn <role>_<method>(&self, <role>_: &<RolePlayerType>)` — private, canonical `<role>_<method>` name.
- **Operations** → `pub fn <snake_case_name>(&self)` on the data struct.
- **Queries** → `pub fn <snake_case_name>(&self)` on the projection struct.

## Receiver Rules

- Functionalities use `&mut self` (the context orchestrates mutation).
- Role methods use `&self` on the context; the role player is passed as an explicit `&` parameter.
- Data operations and projection queries use `&self` by default.

## What the Verifier Enforces

`reen verify` parses the `.rs` file with `syn` and checks:

1. **Struct fields** must exactly match role_players + props (context), attributes (data), or source (projection).
2. **Public methods** must exactly match functionalities (context), operations (data), or queries (projection).
3. **Private methods** must be a superset of role method canonical names. Extra private helpers are allowed.
4. Extra struct fields or missing methods produce a structured diff in DCI vocabulary.

## Implementation Tips

- Start with `todo!()` bodies from scaffold. Fill one method at a time.
- Role methods should only touch their role player parameter — don't reach into `self` fields directly.
- After every edit, the PostToolUse hook runs `reen verify && cargo check`. Fix any diff before continuing.
