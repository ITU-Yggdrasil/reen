# DCI Code Realisation in Rust (Reen)

When implementing or reviewing Rust code generated by Reen, follow these conventions.

## Struct Layout

- **Context**: fields include role players (typed by data/projection name) and props. Additional internal bookkeeping fields (event buffers, caches, counters) are allowed.
- **Data**: fields = attributes. Public struct with named fields.
- **Projection**: a `source` field referencing the underlying data, plus any internal bookkeeping the view needs.

## Method Naming

- **Functionalities** → `pub fn <snake_case_name>(&self)` on the context struct. Change to `&mut self` only when the body requires mutation.
- **Role methods** → `fn <role>_<method>(&self, <role>_: &<RolePlayerType>)` — private, canonical `<role>_<method>` name.
- **Operations** → `pub fn <snake_case_name>(&self)` on the data struct.
- **Queries** → `pub fn <snake_case_name>(&self)` on the projection struct.

## Receiver Rules

- Functionalities default to `&self`; the implementer upgrades to `&mut self` where mutation is needed.
- Role methods use `&self` on the context; the role player is passed as an explicit `&` parameter.
- Data operations and projection queries use `&self` by default.

## What the Verifier Enforces

`reen verify` parses the `.rs` file with `syn` and checks:

1. **Struct fields**: expected fields (role players + props for contexts, attributes for data, source for projections) must be present. Extra fields for internal bookkeeping are allowed on contexts and projections.
2. **Public methods** must exactly match functionalities (context), operations (data), or queries (projection).
3. **Private methods** must be a superset of role method canonical names. Extra private helpers are allowed.

## What the Auditor Checks

`/audit` invokes the DCI-aware auditor agent, which goes beyond structural verification:

1. **Role method responsibilities**: the body of each `<role>_<method>` fn observably performs what the draft citation describes.
2. **Functionality enactment flow**: the public method follows the step sequence from the draft prose.
3. **Invariant enforcement**: guard clauses and validation logic enforce every draft invariant.
4. **Code not in spec**: significant logic that has no basis in the draft or prepared YAML.

## Operation Client Scaffold Shape

Operation clients are generated under `src/apis/<api>/<operation>.rs` from `reen.operation/v1` specs.

**Struct fields** mirror the operation spec:
- `transport_kind`, `url`, `method`, `path` — transport configuration
- `auth_<field>` — authentication credential placeholder
- `input`, `output` — data type placeholders (commented with the spec type name)
- `error_N` — error type placeholders

**Public method set** depends on the output kind:
- `{ call }` — for `single`, `list`, or `none` output kinds (request-response)
- `{ subscribe, next }` — for `stream_of` output kind (streaming/WebSocket)

**What the verifier enforces for operations:**
- Struct name matches the operation name from the spec
- All expected fields are present (transport + auth + input/output/error)
- Public method set matches the kind table above
- Error messages use DCI-adjacent vocabulary: "the `Subscribe` operation on the aisstream api is missing the `auth_apikey` field"

## Web-App Four-Crate Layout

For `web_app` projects, `reen scaffold` emits a Cargo workspace with four crates:

| Crate | Contains | Builds for |
|-------|----------|------------|
| `app-core` | Data, projections, `client_also` contexts | native + WASM |
| `app-server` | `server_only` contexts, operations, server binary | native only |
| `app-client` | WASM entry, DOM event bindings, RPC fetch stubs | WASM only |
| `app-components` | Components, brand, router, `Markup` newtype | native + WASM |

### Where each kind lives

- **Data / Projections** → `app-core`
- **Contexts** → `app-core` if `client_also`, `app-server` if `server_only`
- **Components** → `app-components/src/components/<name>.rs`
- **Brand** → `app-components/src/brand/<name>.rs` + companion `.css`
- **Router** → `app-components/src/router.rs`

### The Markup newtype

`Markup(pub String)` in `app-components::markup`. Framework-neutral — the implementer fills `render()` bodies with whatever templating they choose (raw string building, Askama, Maud, etc.). No escaping; that's the implementer's call.

### Component methods

- `render(&self) -> Markup` — produces the component's HTML representation
- `on_<event>(&self) -> EventOutcome` — one per declared event. Returns `EventOutcome::InvokeDirect` for `client_also` contexts, `EventOutcome::InvokeRemote` for `server_only` contexts, or `EventOutcome::Noop`/`Navigate`

### RPC edges

When a component event binding targets a `server_only` context:
- **Server side**: `POST /_rpc/<context_snake>/<functionality_snake>` handler in `app-server`
- **Client side**: `async fn <context>_<func>() -> Result<String, JsValue>` stub in `app-client`

The RPC path is deterministic from the prepared YAML. Frameworks live in bodies, not in Reen-owned scaffolding.

## Implementation Tips

- Start with `todo!()` bodies from scaffold. Fill one method at a time.
- Role methods should operate on their role player parameter — they express what the role *does* in this context.
- After every edit, the PostToolUse hook runs `reen verify && cargo check`. Fix any diff before continuing.
